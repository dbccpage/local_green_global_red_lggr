The successful-return proof has a legitimate and useful structure:
1. execute proposes a tableau result through phase one, cleanup, and phase two.
2. extract constructs primal/dual vectors and a claimed value.
3. solve returns that certificate only after deciding valid P C.
4. solve_correct proves that an accepted return satisfies that predicate.
5. Weak duality proves optimality; valid_is_real_optimal extends the rational certificate's lower bound to real feasible competitors.
The final checker is a substantive mathematical boundary. The certificate validates primal nonnegativity, every original equality, dual inequalities, and objective equality. Success is therefore not justified by trusting the pivot machinery alone. A defect in candidate generation can produce refusal or failure to find a result without making a checked result mathematically false.
The manuscript's distinction between this proof and a complete phase-invariant proof is accurate. It also correctly declines to claim universal Python-to-Lean refinement. Priority: application/API clarification. Locations: contextuality_lp.evaluate, Section 3.2.
The public contextuality evaluator requires exact compatibility on overlaps and refuses signalling input. That is appropriate for its declared empirical-model domain. The new uncertainty theorem also applies to an observed vector that is merely close to the true vector. Finite-shot fluctuations can violate exact overlap compatibility, so those observations cannot always be passed directly to evaluate.
The lower-level solve_l1 can already optimize against an arbitrary exact observed target once the deterministic columns are fixed. Document an explicit uncertain-observation route: obtain the scenario's columns from its declared measurements, retain the observed table and its uncertainty radius, compute a feasible witness, and interpret only its uncertainty-adjusted margin. Changing the observations to enforce compatibility would itself require accounting for that change.
An exact example illustrates the boundary. Start with the classical mixture and move 1/100 of probability in one context from outcome (0,0) to (1,0). Rows remain normalized and nonnegative, but overlap compatibility fails. The current public API correctly returns SIGNALLING. The raw convex-hull distance is 1/50. The known observation error is also 1/50, so the adjusted guaranteed margin is zero. Interpreting the raw positive distance as contextuality of the true classical model would be wrong; the new theorem correctly prevents that interpretation.
This is a missing connection in an empirical workflow, not a counterexample to the exact-table solver or uncertainty theorem. The present manuscript does not claim an implemented finite-shot inference pipeline.

The most useful next solver extension is independently checked refusal evidence. Currently, infeasible and unbounded are reported algorithm outcomes, not formally certified mathematical conclusions; the manuscript explicitly says so.
For a standard-form problem Ax=b, x≥0, an infeasibility certificate can provide y with Aᵀy≥0 and bᵀy<0. A feasible x would imply bᵀy=xᵀAᵀy≥0, a contradiction. An unboundedness certificate can provide a feasible x0 and a direction d≥0 with Ad=0 and cᵀd<0; then x0+λd remains feasible while its objective tends downward without bound. Resource exhaustion should remain a separate, uncertified outcome.
These are established certificate forms, not proposed historical novelties. The [CGAL solver manual](https://doc.cgal.org/latest/QP_solver/index.html) documents independent certificates for optimality, infeasibility, and unboundedness. Adding corresponding checked return paths here would extend the present certificate architecture to more outcomes and make refusal semantics more useful.
For the broader RSI application, the next substantial result remains a refinement tying an implemented memory transformation and enforced action gate to a declared safety invariant. More arithmetic lemmas alone will not establish that connection. The manuscript already identifies this as an open application, which is appropriate.
